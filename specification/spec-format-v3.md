# Spec Format Specification

Version 3.0

Supersedes version 2.0 (`spec-format-v2.md`). Section 13 maps every v2
construct to its v3 equivalent and states the conversion, which is
deterministic.

## 0. Why version 3

Version 2 proved the plan complete: every criterion verified by a test, every
test owned by a task, every path exercised by a smoke test. It did so by
storing the proof in a fourth artifact, `test_spec.json`, whose tests were the
criteria restated: 404 tests for 442 criteria across ten packages, one test
per criterion in 93 % of cases, each test twice the size of the criterion it
verified. The plan's progress lived in `tasks.json`, so every task move
rewrote a contract artifact and the package's render. The last task was
always the same integration task, authored by hand, and every id carried the
package's prefix that a rule then checked.

Version 3 keeps what version 2 proved and moves the proof into the shape of
the data: **a criterion carries its check, a path carries its smoke check,
and the plan owns criteria.** Four cross-file rules become schema
constraints, one artifact and one generation phase disappear, progress moves
to a file of its own so that the contract is immutable from activation, the
integration task is derived from the package, the fields nothing used are
gone, and a small change fits a `lite` package with no paths.

Design rules, unchanged from version 2:

1. One concept, one place. No section may restate another section.
2. Derived data is never stored. Coverage, traceability and the integration
   task are computed.
3. Structure over string matching. Validation never greps for words.
4. The plan is the contract. Validation proves the plan covers the spec.
5. Fewer, longer items beat many short ones. Token budgets are finite.

---

## 1. Scope

This document defines the on-disk format for a specification package
("spec"): the durable artifact that captures design intent, acceptance
criteria with their checks, and the implementation plan for one cohesive
feature.

| File | Format | Required | Purpose |
|---|---|---|---|
| `prd.md` | Markdown with YAML frontmatter | yes | Narrative intent: the "why" and "what" |
| `requirements.json` | JSON (schema-validated) | yes | What the system must do, as EARS criteria each with its check, plus the end-to-end execution paths each with its smoke check |
| `tasks.json` | JSON (schema-validated) | yes | One flat list of implement tasks; each task owns criteria |
| `progress.json` | JSON (schema-validated) | written by the tools | The state of every task, the integration task included, and when it last changed |
| `architecture.md` | Markdown (free-form) | no | Modules, interfaces, data models, technology choices |
| `spec.md` | Markdown (generated) | written by every save | The contract rendered as one document (§3) |

The first three files are the package's **contract**. `progress.json` is not:
it is written by the tools, never read as intent, and is the one file a task
move changes.

---

## 2. Terminology

| Term | Definition |
|---|---|
| Spec | A package of the files above representing one feature |
| Spec root | The directory containing all specs, e.g. `.specs/` |
| Operator | A human who authors PRDs and reviews specs |
| Coordinator | The agent that generates and mutates the JSON artifacts |
| Coder | The agent that executes one task at a time |
| Criterion | One testable EARS statement inside a requirement, with its check |
| Check | How a criterion is verified: its own, or the same as another's |
| Path | An execution path: an end-to-end scenario from entry point to side effect, with its smoke check |
| Task | One entry of `tasks.json`; the unit of dispatch to a coder |
| Integration task | The derived last task of a `full` package (§8.4) |
| Profile | `full` or `lite` (§4.1, §6.5) |
| EARS | Easy Approach to Requirements Syntax |

## 3. Folder layout, naming, completeness

Unchanged from v2 §3: `<spec_root>/{NN}_{snake_case_name}/`, monotonically
increasing `NN`, `archive/` for superseded and archived specs, the three
contract files must exist for the spec to be valid, bootstrap mode during
creation.

Beside its artifacts a package holds `spec.md`, the combined render of §11.1
with no scope and no budget, under one header line and a blank line:

```
<!-- Generated by afspec from prd.md, requirements.json, tasks.json and architecture.md. Do not edit: change those files, or run speca <package> --render. -->
```

It is generated, not canonical: every save of the package writes it, in the
same all-or-nothing write as the artifacts. It renders the contract and never
the progress, so a task move leaves it byte for byte as it was. It is never
read as data, and is not part of the package's contract; rule `rendered`
(§10.2) reports one that is missing or no longer the render, and
`speca <package> --render` writes it again.

## 4. `prd.md`

### 4.1 Frontmatter

```yaml
---
spec_id: "05"
spec_name: "my_feature"
title: "Human-readable title"
status: "draft"                 # draft | active | sealed | superseded | archived
created_at: "2026-05-18T12:00:00Z"
intent_hash: null               # set at draft → active
contract_hash:                  # set at draft → active; absent before
  requirements.json: "<64 hex digits>"
  tasks.json: "<64 hex digits>"
schema_version: 3
profile: "full"                 # optional: full | lite
steering_version: "2.0.1"       # optional
source: "docs/prds/feature.md"  # optional
supersedes: []                  # optional
---
```

| Field | Type | Required | Description |
|---|---|---|---|
| `spec_id` | string | yes | Numeric prefix as string. Must match the folder prefix. |
| `spec_name` | string | yes | Snake-case slug. Must match the folder suffix. |
| `title` | string | yes | Human-readable title. |
| `status` | enum | yes | Lifecycle state (§9). |
| `created_at` | ISO 8601 | yes | Immutable after creation. |
| `intent_hash` | string or null | yes | SHA-256 of the `## Intent` body. Null while `draft`. |
| `contract_hash` | object | no | Recorded at `draft → active`: `requirements.json` and `tasks.json`, each the SHA-256 (64 lowercase hex digits) of that file's canonical encoding with every extension key (§10.1) left out. A package that is `active` and has one **requires evidence** (§8.3): while either file no longer hashes to it, the package's task moves and its sealing are refused. Absent for a draft and for a package activated before it was recorded, whose tasks close without evidence. |
| `schema_version` | integer | yes | `3`. |
| `profile` | enum | no | `full` (the default when absent) or `lite`. A `lite` package has at most three requirements, no execution path, no smoke check and no integration task (§6.5, rule C7). A package is promoted to `full` by adding a path and removing the field. |
| `steering_version` | string | no | As in v2 §4.1. |
| `source`, `supersedes` | | no | As in v2. Omitted means empty. |

Removed from v2: `updated_at`, which is `progress.json`'s (§8.7); `owner` and
`tags`, which no package used. A team that wants them writes extension keys
(§10.1).

### 4.2 Body

Unchanged from v2 §4.2: `# {title}` followed by a mandatory `## Intent`
section (the only machine-read section, hashed at activation), then any
operator-discretion sections. A package's glossary, when it has one, is a
`## Glossary` section of the PRD: documentation, read by people, validated
by nothing. Architectural content belongs in `architecture.md`.

The scope rule of v2 §4.2 stands: at most 10 requirements, or a split.

## 5. `architecture.md`

Unchanged from v2 §5: optional, free-form, no frontmatter, not validated.

## 6. `requirements.json`

### 6.1 Top-level schema

```json
{
  "$schema": "https://agent-fox.dev/schemas/requirements.v3.json",
  "spec_id": "05",
  "spec_name": "my_feature",
  "schema_version": 3,
  "requirements": [],
  "execution_paths": [],
  "external_apis": []
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `$schema` | string | yes | Schema URI. |
| `spec_id`, `spec_name` | string | yes | Must match `prd.md`. |
| `schema_version` | integer | yes | `3`. |
| `requirements` | array | yes | Requirement objects (§6.2). At least one. |
| `execution_paths` | array | no | Path objects (§6.3). At least one in a `full` package, none in a `lite` one (rule C7). |
| `external_apis` | array | no | Verified external symbols, as v2 §6.4. |
| `handoffs` | array | no | What this package leaves for a later package to call, register into or fill (§6.4.1). |

Removed from v2: `introduction`, which restated `## Intent`; `glossary`,
which is a PRD section (§4.2).

### 6.2 Requirements and criteria

```json
{
  "id": "REQ-1",
  "title": "Agent mode output",
  "rationale": "Agents parse stdout; any non-JSON byte breaks them.",
  "system": "spec binary",
  "criteria": [
    {
      "id": "REQ-1.1",
      "pattern": "state_driven",
      "condition": "AF_AGENT=1 is set in the environment",
      "action": "write only JSON to stdout and route all progress output to stderr",
      "contract": "stdout parses as a single JSON object",
      "check": {
        "kind": "unit",
        "setup": ["a command whose result is a map"],
        "pseudocode": "in cmd/spec/main_test.go beside TestMain_JSONOnly: r = run(env={AF_AGENT:1}, 'spec list'); assert parse_json(r.stdout); assert r.stderr has the progress"
      }
    },
    {
      "id": "REQ-1.2",
      "pattern": "unwanted",
      "condition": "an unhandled error occurs while AF_AGENT=1 is set",
      "action": "write {\"ok\": false, \"error\": <message>} to stdout and exit",
      "contract": "exit code 1; stdout is {\"ok\": false, \"error\": string}",
      "check": {
        "kind": "unit",
        "pseudocode": "r = run(env={AF_AGENT:1}, 'spec status 99_missing'); assert r.code == 1; j = parse_json(r.stdout); assert j.ok == false; assert len(j.error) > 0"
      }
    },
    {
      "id": "REQ-1.3",
      "pattern": "unwanted",
      "condition": "stdout is a closed pipe while writing the JSON result",
      "action": "suppress the write error and exit with the command's own exit code",
      "contract": "no panic; exit code unchanged by the write failure",
      "check": { "same_as": "REQ-1.2" }
    }
  ]
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | `REQ-{N}`, N sequential from 1. |
| `title` | string | yes | Short descriptive title. |
| `rationale` | string | no | One sentence: why this requirement exists. |
| `system` | string | no | The component that acts, for every criterion of the requirement that names none. |
| `criteria` | array | yes | Criterion objects. At least one. |

There is no separate edge-case list: an edge case is a criterion, usually
`unwanted`. A correctness property is a `ubiquitous` criterion whose action
starts with "for any …", verified by a `property` check when a table of
representative inputs cannot establish it and by a `unit` check otherwise.

#### 6.2.1 Criterion

Each criterion is one EARS sentence decomposed into fields, with its check.
The rendered sentence is derived; the fields are the source of truth.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | `REQ-{N}.{C}`, C sequential from 1 within the requirement. |
| `pattern` | enum | yes | `ubiquitous`, `event_driven`, `state_driven`, `unwanted`, `optional`. |
| `condition` | string | all but `ubiquitous` | The clause after the pattern keyword: the trigger, state, error condition or feature. A second condition is written into it, joined with "and". Must be absent for `ubiquitous`. |
| `system` | string | no | The component that acts. Defaults to the requirement's `system`, then to `"system"`, when rendering. |
| `action` | string | yes | What the system must do. Testable and unambiguous. |
| `contract` | string | `unwanted` | What the caller observes, and what the check asserts: return value, exit code, status code, emitted event. Required for `unwanted`; recommended whenever the result is consumed by something else. |
| `check` | object | yes | How the criterion is verified (§6.2.2). |

| `pattern` | Rendered sentence |
|---|---|
| `ubiquitous` | THE {system} SHALL {action} |
| `event_driven` | WHEN {condition}, THE {system} SHALL {action} |
| `state_driven` | WHILE {condition}, THE {system} SHALL {action} |
| `unwanted` | IF {condition}, THEN THE {system} SHALL {action} |
| `optional` | WHERE {condition}, THE {system} SHALL {action} |

When `contract` is present the renderer appends a second line:
`→ {contract}`. The contract is always rendered.

Removed from v2: `guard` and the `complex_event` pattern. A criterion that
needed both is written with the two conditions in `condition`.

#### 6.2.2 Check

A check is the test of its criterion, in the three fields a test adds that the
criterion does not have. The criterion's `condition` is the test's given, its
`action` the when, and its `contract` the then.

| Field | Type | Required | Description |
|---|---|---|---|
| `kind` | enum | own check | `unit` (one component, collaborators may be stubbed), `integration` (two or more real components, only external I/O stubbed), `property` (an invariant over an input domain the pseudocode names). |
| `setup` | array of strings | no | The preconditions the `condition` does not state. |
| `pseudocode` | string | no | Language-agnostic assertions. It names the function, handler or command the check exercises and, when the repository has a test file for it, that file and the existing test it extends. |
| `same_as` | string | shared check | The id of a criterion of this package whose own check verifies this one too, or of a path whose smoke check does. |

A check is either its own (`kind`, with `setup` and `pseudocode` optional) or
shared (`same_as` alone). A shared check never points at a criterion whose
check is itself shared (rule C3), so a reader follows one link. The 7 % of
criteria that one test verified in v2 are written as one criterion with the
check and its neighbours with `same_as`.

### 6.3 Execution paths

```json
{
  "id": "PATH-1",
  "title": "Operator creates a spec from a PRD file",
  "steps": [
    { "actor": "operator",    "action": "runs `spec new prd.md --name feature`" },
    { "actor": "spec binary", "action": "validates the PRD path and the name" },
    { "actor": "spec binary", "action": "writes prd.md and the JSON scaffolds" },
    { "actor": "spec binary", "action": "prints {\"ok\": true, \"spec_dir\": …} to stdout" }
  ],
  "smoke": {
    "real_components": ["spec binary", "file system"],
    "setup": ["a repository with no spec root"],
    "end_state": [".specs/01_feature holds prd.md, requirements.json and tasks.json", "stdout is one JSON object with ok true"],
    "pseudocode": "extends TestSpec_WritesPackage in cmd/spec/main_test.go: r = run('spec prd.md'); assert r.code == 0; assert exists(dir + '/tasks.json')"
  }
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | `PATH-{N}`. |
| `title` | string | yes | The end-to-end scenario. |
| `steps` | array | yes | At least two `{actor, action}` steps. |
| `smoke` | object | yes | The path's smoke check (§6.3.1). |

Path rules are unchanged from v2 §6.3: a path starts at a user action, CLI
command, API call or scheduled trigger; ends at a concrete side effect; uses
logical actors; and, when several specs form a dependency chain, the last
spec in the chain owns a path that crosses every spec boundary.

#### 6.3.1 Smoke check

A smoke check proves the wiring of its path: it runs the path once with real
components and asserts the end state. It does not assert again the criteria
the checks verify.

| Field | Type | Required | Description |
|---|---|---|---|
| `real_components` | array of strings | yes | Non-empty. The components that must not be mocked. |
| `setup` | array of strings | no | Preconditions. |
| `end_state` | array of strings | yes | Non-empty. The side effects at the end of the path. |
| `pseudocode` | string | no | Language-agnostic assertions, naming the existing end-to-end test it extends when there is one. |

### 6.4 External APIs (optional)

As v2 §6.4.

#### 6.4.1 Handoffs (optional)

A handoff is an extension point or entry point a package offers and leaves
for a named package that lands later to call, register into or fill.

```json
{ "id": "H-1", "what": "after-landing hooks of internal/land", "to": "24", "criteria": ["REQ-2.1"] }
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | `H-N`, unique within the package (C2). |
| `what` | string | yes | The extension point or entry point left. |
| `to` | string | yes | The spec id of the receiving package, which must depend on this one directly or transitively (cross-spec rule `cross_spec_handoff_direction`, §10.3). |
| `criteria` | array of strings | yes | At least one criterion id of this package (C4) that depends on the handoff being wired; no requirement ids, no repeats. |

The receiving package's tasks name what they take in `takes_handoffs`
(§7.2). Validating the receiver warns `handoff_not_taken` for each inbound
handoff no task takes, an error under `speca --validate --strict-handoffs`.

### 6.5 Requirement quality rules

1. **[schema]** Every criterion has a non-empty `action` and a `check`; every
   path has a `smoke` check.
2. **[validator, error]** Every `unwanted` criterion has a `contract` (C6).
3. **[validator, error]** A `full` package has at least one path; a `lite`
   package has none and at most three requirements (C7).
4. **[validator, warning]** A spec has at most 10 requirements; a requirement
   has at most 8 criteria. Beyond that, split the spec.
5. **[generation hint, review rubric]** Criterion fields avoid vague words
   (`appropriate`, `properly`, `correctly`, `reasonable`, `relevant`,
   `adequate`, `suitable`, `as needed`, `if necessary`, `etc`). The validator
   matches no words.
6. **[generation instruction]** For every requirement the coordinator
   considers, and where applicable writes a criterion for: empty or null
   input; boundary values; operation failure; authorization failure;
   concurrent operation. For anything that spawns processes, loops, retries
   or calls a service: timeout, resource cleanup on failure, iteration cap,
   and the rule that library code returns errors instead of terminating the
   process.
7. **[generation instruction]** Prefer measurable constraints over qualitative
   language.
8. **[generation instruction]** One check per behaviour. Criteria whose checks
   differ only in the input share one check over a table of inputs: the
   owner carries it and names the cases in `pseudocode`, the others say
   `same_as`. A `property` check only for an invariant a table cannot
   establish. For every `unwanted` criterion the check asserts the
   caller-observable outcome of its `contract`, not merely "an error
   occurred". No check checks an artefact (a struct's fields, a constant's
   value, a document's content) rather than a behaviour. A behaviour an
   existing test of the repository already verifies keeps its check, which
   names that test in `pseudocode`.

## 7. `tasks.json`

One flat, ordered list of implement tasks. A task is the unit of dispatch:
one coder session, one task. The checks a task's criteria carry are written
and made to pass inside the task; there are no separate "write tests" tasks,
and no integration task is stored (§8.4).

### 7.1 Top-level schema

```json
{
  "$schema": "https://agent-fox.dev/schemas/tasks.v3.json",
  "spec_id": "05",
  "spec_name": "my_feature",
  "schema_version": 3,
  "test_commands": {
    "all_tests": "go test ./... -count=1",
    "linter": "go vet ./...",
    "spec_tests": "go test ./cmd/spec/... -count=1",
    "evidence_tests": "./scripts/run-tests {tests}"
  },
  "dependencies": [],
  "tasks": []
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `test_commands` | object | yes | `all_tests` and `linter` required; `spec_tests` optional; `affected_tests` optional, the command that runs the tests a change can affect, holding the placeholder `{base}` (the commit the change starts from) exactly once (rule `affected_tests_base`); `evidence_tests` optional, the command that runs the tests it is given and prints, on stdout, one line per test, `{"test": <identifier>, "status": "pass" \| "fail" \| "error" \| "missing" \| "skipped"}`, holding the placeholder `{tests}` exactly once as an argument of its own once the command is split on white space and quotes (rule `evidence_tests_placeholder`), which the tools replace with one argument per test identifier. Without `evidence_tests`, a repository with a `go.mod` uses the tools' own Go runner, whose identifiers are `<package>:<Test>[/<subtest>]`. Must use the project's real tooling. |
| `dependencies` | array | yes | Cross-spec dependencies, as v2 §8.2. May be empty. |
| `tasks` | array | yes | Task objects (§7.2). At least one. |

### 7.2 Task

```json
{
  "id": 3,
  "title": "Agent mode: JSON-only stdout and error envelope",
  "criteria": ["REQ-1"],
  "steps": [
    "Add isAgentMode() reading AF_AGENT and thread it through the root command",
    "Route the banner and spinner to stderr; make emit() the only stdout writer",
    "Wrap the Execute() error path: in agent mode print {ok:false,error} and exit 1",
    "Treat EPIPE from emit() as success so a closed pipe never changes the exit code"
  ],
  "touches": ["cmd/spec/root.go", "cmd/spec/emit.go", "cmd/spec/main_test.go"],
  "depends_on": [1],
  "done_when": ["AF_AGENT=1 spec list | jq . succeeds with no banner text on stdout"]
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | integer | yes | Sequential from 1. Order in the array is the default execution order. |
| `title` | string | yes | Imperative, specific. |
| `criteria` | array of strings | yes | Non-empty. Requirement ids or criterion ids this task satisfies; a requirement id means all of its criteria. |
| `steps` | array of strings | yes | Non-empty. What to do, in order: a behaviour to add or a decision already taken, not an edit. No line numbers, no quoted code. |
| `touches` | array of strings | no | Files, packages or modules the task is expected to create or modify, the test files it extends among them. |
| `depends_on` | array of integers | no | Task ids that must be `done` first. Absent means "the previous task" in array order. Must reference lower ids. The generator omits one that names only the previous task. |
| `done_when` | array of strings | no | Extra completion checks beyond the implicit ones. |
| `takes_handoffs` | array of strings | no | The handoffs the task takes, each `<spec id>:H-N` (`"24:H-1"`), at least one, no repeats; each must name a handoff that package declares to this one (cross-spec rule `cross_spec_handoff_taken`). |

Removed from v2: `kind` (every stored task is an implement task), `tests`
(the checks are on the criteria the task owns), `state` (§8.7) and
`optional` (a task that may be skipped is a task that should not be in the
plan).

**Implicit definition of done for every task:** the checks of the criteria it
owns exist as tests, are executable and pass; `test_commands.all_tests`
passes; `test_commands.linter` passes; every `done_when` entry holds. The
coder works test-first: write each check as the project's own test, run it
and see it fail, then implement `steps` until it passes.

### 7.3 Plan quality rules

1. **[validator, error]** Every criterion is owned by at least one task,
   directly or through its requirement (C5).
2. **[validator, error]** Every id in `criteria` and `depends_on` resolves;
   `depends_on` forms a DAG over lower ids (C4).
3. **[validator, warning]** A task has at most 12 steps; a spec has at most
   12 tasks.
4. **[generation instruction]** Group by requirement, not by layer: a task
   delivers one or two requirements end to end, so that each task leaves the
   system in a working state.
5. **[generation hint]** A step says a behaviour to add or a decision already
   taken. The generator sends a tasks artifact that names a line of a file
   back to its phase once; the validator does not check it.

## 8. Progress and the integration task

### 8.1 Task state machine

```
pending ──→ in_progress ──→ done
   │             │            │
   │             └──→ pending ┘   (released, or reopened after an upstream change)
   └──→ dropped
```

| State | Allowed next states |
|---|---|
| `pending` | `in_progress`, `dropped` |
| `in_progress` | `done`, `pending` |
| `done` | `pending` |
| `dropped` | (terminal) |

### 8.2 Readiness

A task is ready when it is `pending` and everything it depends on is `done`:
its `depends_on` when the field is present (an empty list means none), else
the task before it in plan order, the first task having none. The integration
task is ready when every task of the plan is `done` or `dropped`. The next
task is the first `in_progress` task in id order, else the first ready one.

### 8.3 `progress.json`

```json
{
  "$schema": "https://agent-fox.dev/schemas/progress.v3.json",
  "spec_id": "05",
  "spec_name": "my_feature",
  "schema_version": 3,
  "updated_at": "2026-05-19T09:30:00Z",
  "tasks": [
    { "id": 1, "state": "done",
      "evidence": [
        { "covers": "REQ-1.1", "tests": [
          { "test": "./cmd/x:TestA",
            "failed": { "at": "2026-05-19T09:10:00Z", "tree": "4b825dc6…" },
            "passed": { "at": "2026-05-19T09:25:00Z", "tree": "9c2f1e0a…" } } ] }
      ] },
    { "id": 2, "state": "in_progress" },
    { "id": 3, "state": "pending" }
  ]
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `$schema`, `spec_id`, `spec_name`, `schema_version` | | yes | As the other artifacts. |
| `updated_at` | string | yes | When a task last changed state, RFC 3339. The empty string when none has. |
| `tasks` | array | yes | One `{id, state}` per task of the plan and one for the integration task, in id order. A task with no entry is `pending`. Every entry names a task of the plan or the integration task, each at most once (C8). |
| `tasks[].evidence` | array | no | In a package that requires evidence (§4.1), the tests that cover each criterion the task owns (for the integration task, each execution path): entries of `covers` (the id), `tests` (1 to 50, each `{test, failed?, passed?}`, a run being `{at, tree?}`, `tree` the git tree id of the working tree the run was on) and an optional `no_red` (1 to 500 characters), the reason its tests need not be seen failing first. Written by the tools: the failing runs before the task is implemented, the passing runs when it closes. A move to `pending` removes it. |

The file is written by every save of the package, and `Spec.SaveProgress`
writes it alone. A package without it loads with every task `pending`. It is
never rendered into `spec.md`, never hashed, and never a reason to refuse a
package: a task move on an active package writes this one file.

**Closing a task on evidence.** In a package that requires evidence, a task
moves to `done` only when every criterion it owns (for the integration task,
every path) has an evidence entry, every test of an implement task has a
recorded failing run or is exempt (every entry that lists it carries
`no_red`), and every test, run at the close, passes. The tools record the
failing runs in a call of their own while the task is `in_progress`, before
its implementation exists, and the close records the passing runs with the
state. A tool may close a task without these checks only when asked to
explicitly, and says so.

### 8.4 The integration task

A `full` package has one integration task, which is **derived** and not
stored. It is task `N+1`, where `N` is the highest task id of the plan, with
kind `integration`; the stored tasks have kind `implement`. Every tool that
lists, renders, counts or moves tasks includes it under that id. Its state is
its entry in `progress.json`.

Its content is computed from the package:

- title: "Verify every execution path end to end";
- criteria: none;
- `depends_on`: every task of the plan;
- `touches`: the union of every task's `touches`, in order, each once;
- steps: for every path, run its smoke check with its real components and
  confirm its end state, and trace the path through the real code, confirming
  each step calls the next and no stub remains; for every criterion with a
  contract, confirm the producer's result is consumed by a caller in
  production code, not only by tests; search every path in `touches` for stub
  markers; and, when the package depends on other packages, confirm the entry
  points those packages own are called from production code;
- done when: `test_commands.all_tests` and `test_commands.linter` pass.

An execution path that is not live in production code fails this task.
Errata or deferrals do not satisfy it. A `lite` package has no paths and no
integration task.

### 8.5 Derived traceability

```
criterion → check (its own, or the one it is the same as) → tasks (from task.criteria)
path      → smoke check                                   → integration task
```

No traceability array is stored, so it cannot drift.

### 8.6 Dependencies on other specs

As v2 §8.2: `{spec, reason}`, at spec granularity.

### 8.7 What changes after activation

The three contract files change only by a lifecycle move (§9): activation
writes `intent_hash` and `status`, sealing and archiving write `status`,
superseding writes `status` and the banner. A task move writes
`progress.json` alone. `spec.md` changes with the contract and never with
the progress.

## 9. Lifecycle

Unchanged from v2 §9: `draft → active → sealed`, optional `superseded` and
`archived`; intent hash computed at `draft → active` and enforced afterwards;
superseding adds a deprecation banner and moves the old spec to `archive/`.
Sealing a package with an open task, the integration task included, is
refused without `--force`.

## 10. Validation

### 10.1 Schema validation

Per-file JSON Schema validation (`*.v3.json`): `prd-frontmatter.v3.json`,
`requirements.v3.json`, `tasks.v3.json` and, when the file is present,
`progress.v3.json`. Rejects unknown fields, missing required fields, bad
enums, a criterion without a check, a path without a smoke check, a check
that mixes its two forms.

**Extension keys** are as in v2 §10.1: every object of the four schemas
accepts a key that begins with `x-`, kept by every save, refused in a model's
artifact, not rendered.

**Another version.** A package whose `schema_version` is neither absent nor
`3` is reported with one `schema_version` error that names the version and
`speca <package> --migrate`, and nothing else of it is validated.

### 10.2 Cross-file integrity

All rules are errors.

| # | Rule | Artifacts |
|---|---|---|
| C1 | `spec_id` and `spec_name` agree across `prd.md`, `requirements.json`, `tasks.json`, `progress.json` when present, and the folder name. | all |
| C2 | Every id matches its format (Appendix A), a criterion id is under its requirement, and every id is unique within its family (a handoff id among the handoffs). | requirements, tasks |
| C3 | Every `check.same_as` names a criterion of this spec whose check is its own and is not the criterion itself, or a path of this spec. | requirements |
| C4 | Every `task.criteria` entry resolves to a requirement or a criterion; every `depends_on` entry resolves to a lower task id; every handoff's `criteria` entry resolves to a criterion. | tasks → requirements |
| C5 | Every criterion is owned by at least one task, directly or through its requirement. | requirements ← tasks |
| C6 | Every `unwanted` criterion has a non-empty `contract`. | requirements |
| C7 | A `full` package has at least one execution path; a `lite` package has no execution path and at most three requirements. | prd.md, requirements |
| C8 | Every entry of `progress.json` names a task of the plan or the integration task, each at most once. | progress → tasks |
| `affected_tests_base` | `test_commands.affected_tests`, when present, holds `{base}` exactly once. | tasks |

Warnings (never block): scope limits (§6.5.4, §7.3.3), criteria without a
`contract` whose action mentions an error outcome. Vague wording and line
references are the generator's hints, not the validator's.

Rule `rendered` is as in v2 §10.2: `spec.md` must be the package's render,
an error for a draft or active package and a warning otherwise, a warning
when absent.

### 10.3 Cross-spec

The cross-spec rules check: every `dependencies[].spec` exists; the
dependency graph is acyclic; and, for each dependency edge where both
packages have execution paths, the downstream spec has at least one path step
whose actor also appears in an upstream path (error). An actor matches by
name, ignoring case. The v2 glossary comparison is gone with the glossary.

The handoff rules (§6.4.1): a handoff's `to` names a package under the spec
root, not the package itself, that depends on the sender directly or
transitively (`cross_spec_handoff_direction`, an error of the sender); a
`takes_handoffs` entry names a handoff its package declares to the taker
(`cross_spec_handoff_taken`, an error of the taker); and an inbound handoff
no task of the receiver takes is the warning `handoff_not_taken`, an error
when the caller asks for strict handoffs.

### 10.4 Steering version

As v2 §10.5.

## 11. Rendering

Rendering is deterministic: same JSON in, same Markdown out.

### 11.1 Targets

| Target | Content |
|---|---|
| Per-file | Markdown for one artifact. |
| Combined | PRD frontmatter and body, then `architecture.md` if present, then requirements (each criterion as its sentence, its contract and its check; each path with its steps and smoke check; the external APIs), then tasks (the test commands, the dependencies, every task of the plan, then the integration task). No task state. |
| Scoped to task `N` of the plan | PRD frontmatter and body without its `## Background` and `## Requirements` sections, with one line in their place; the architecture unfiltered; the requirements that own the task's criteria in full and all others as one line each; the paths a `same_as` of those criteria names in full and all others as one line each; every external API; the test commands and dependencies; task `N` in full and all other tasks, the integration task included, as one line each. |
| Scoped to the integration task | The PRD and architecture as above; every requirement as one line; the criteria that carry a contract, each with it; every path in full with its smoke check; every external API; the test commands and dependencies; the integration task in full and every other task as one line. |

### 11.2 Rules

- Every criterion renders as its EARS sentence followed by `→ {contract}`
  when a contract exists, then its check: the kind, the setup, the pseudocode,
  or the id it is the same as.
- Every path renders its steps and its smoke check in full.
- Every task renders `steps`, `touches`, `criteria`, `done_when` and the
  implicit definition of done; the integration task renders its computed
  content the same way.
- Nothing in the contract is dropped, with the exceptions of v2 §11.2 (the
  `$schema` URIs, the identity copies, the `pattern`, the extension keys).
  The progress is not in the contract and is not rendered.
- A budget drops the architecture first, then the `setup` and `pseudocode` of
  every check and smoke check.
- A value inside a table cell has `|` escaped and newlines written as `<br>`.

## 12. Generation contract

1. **Sequential with full context.** Artifacts are generated in the order
   requirements → tasks. The tasks step receives the complete requirements
   artifact, every id and every sentence.
2. **Validate inline, repair inline.** After the requirements step the
   pipeline runs the schema and C1, C2, C3, C6 and C7; after the tasks step
   the schema and C1 to C7. Violations go back to the model for repair before
   anything is written. A generation that ends with an invalid spec is a
   failed generation.
3. **Examples match the schema.**
4. **Scope first.** Before writing requirements the coordinator decides
   whether the PRD fits in 10 requirements; if not, it reports that the PRD
   must be split. A PRD of at most three requirements with no flow that
   crosses components may be a `lite` package; the PRD phase decides and the
   requirements phase is held to it.
5. **Language from the project.** Test commands, stub markers and pseudocode
   idioms come from the project's manifest, never from a default.
6. **The integration task is not generated.** The tasks phase writes
   implement tasks only.

## 13. Migration from v2

| v2 construct | v3 |
|---|---|
| `test_spec.json`, `tests[]` (`TS-NN-N`) | gone; each criterion carries `check`, each path `smoke` |
| `test.kind`, `given`, `pseudocode` | `check.kind`, `check.setup`, `check.pseudocode` on the criterion that owns the test |
| `test.title`, `test.when` | dropped; they restate the criterion |
| `test.then` | the criterion's `contract` when it had none; dropped otherwise |
| a test verifying several criteria | the first criterion (in `verifies`) owns the check; the others say `check: {same_as}` |
| a criterion verified by a smoke test alone | `check: {same_as: "PATH-N"}` |
| `smoke` test: `real_components`, `given`, `then`, `pseudocode` | `path.smoke`: `real_components`, `setup`, `end_state`, `pseudocode` |
| `{spec_id}-REQ-N`, `{spec_id}-REQ-N.C`, `{spec_id}-PATH-N` | `REQ-N`, `REQ-N.C`, `PATH-N` |
| `complex_event` with `guard` | `event_driven` with `condition` = "{condition} and {guard}" |
| `criterion.system`, the same on every criterion of a requirement | `requirement.system` |
| `introduction` | dropped |
| `glossary` | a `## Glossary` section appended to the PRD body |
| frontmatter `updated_at` | `progress.json` `updated_at` |
| frontmatter `owner`, `tags` | `x-owner`, `x-tags` when set |
| `task.kind`, `task.tests`, `task.optional` | dropped |
| the `integration` task | removed from the plan; its state is the progress entry of task `N+1` |
| `task.state` | `progress.json` entries |
| C3, C4, C5, C7, C9, C11 | the schema (a check and a smoke check are required) and C3 (`same_as` resolves) |
| C6, C8, C10 | C4, C5, C6 |
| — | C7 (the profile), C8 (the progress) |

A v2 spec converts to v3 deterministically by the table above. The
conversion refuses a package with a criterion no test verifies or a path no
smoke test verifies, which v2 rules C4 and C5 forbid, so a valid v2 package
always converts. Extension keys on tests and on the integration task are
lost; every other extension key keeps its object. `speca <package> --migrate`
performs the conversion in place, whatever the package's status, and
`speca --migrate --all` converts every package of a spec root and its
archive.

## Appendix A: ID formats

| Entity | Format | Example |
|---|---|---|
| Requirement | `REQ-{N}` | `REQ-3` |
| Criterion | `REQ-{N}.{C}` | `REQ-3.2` |
| Execution path | `PATH-{N}` | `PATH-1` |
